# データベース

## 接続

- 接続先は環境変数 `DATABASE_URL` で指定します。未設定の場合は起動時にエラーになります (`src/db/index.ts`, `drizzle.config.ts`)。
- ローカルでは `compose.yaml` の `db` サービス (PostgreSQL 18) を使用します。
- 初回起動時に `db/init/init-user-psql.sh` が実行され、以下が作成されます。

| 種類 | 名前 | 備考 |
| --- | --- | --- |
| ユーザー | `developer` / `password` | `CREATEDB` 権限。開発者用 |
| ユーザー | `ai` / `password` | `CREATEDB` 権限。AI エージェント (`ai` コンテナ) 用 |
| DB | `api_dev` | 開発用 (所有者 `developer`) |
| DB | `api_test` | テスト用 (所有者 `developer`) |
| DB | `api_ai` | AI エージェントの検証用 (所有者 `ai`) |

- 各 DB は `PUBLIC` の `CONNECT` 権限を外しているため、所有者 (と `postgres`) のみ接続できます。`ai` ユーザーは `api_ai` 以外に接続できません。
- `init-user-psql.sh` は DB の volume が空のとき (初回起動時) のみ実行されます。変更を反映するには volume を削除して作り直します。

### リレーション

Drizzle のリレーション (`db.query` の `with` で利用) は、各テーブルのスキーマファイルにテーブル定義と一緒に `<テーブル名>Relations` として定義します。
`schema/index.ts` から export されるため、`src/db/index.ts` で `drizzle()` に渡す `schema` に含まれます。drizzle-kit (マイグレーション) はリレーションを参照しません。

- 1 つの関連は両側のテーブルにそれぞれ定義します (例: `users` に `many`、`chat_sessions` に `one`)。
- テーブル同士が互いを import する循環になりますが、参照はコールバック内のみのため問題ありません。
- Drizzle 1.0 ではリレーションの API が `defineRelations` に変わるため、移行時に `defineRelationsPart` で機能ごとのファイルに分け直す予定です。

| テーブル | 名前 | 種類 | 対象 |
| --- | --- | --- | --- |
| `users` | `chatSessions` | many | `chat_sessions` |
| `chat_sessions` | `user` | one | `users` (`chat_sessions.user_id` → `users.id`) |

### 共通カラム

`src/db/schema/columns/timestamps.ts` の `timestamps` をスプレッドすると `created_at` / `updated_at` が追加されます。
`updated_at` の自動更新は Drizzle の `$onUpdate` によるもので、DB トリガーではありません (生 SQL での更新時は反映されません)。

## マイグレーション

マイグレーションファイルは drizzle-kit で `drizzle/` に生成します。各マイグレーションには、戻すための SQL を `drizzle/down/` に同じファイル名で手書きします ([ロールバック](#ロールバック))。

| ファイル | 内容 |
| --- | --- |
| `0000_create_admin_users.sql` | `admin_users` テーブル作成 |
| `0001_create_users.sql` | `users` テーブル作成 |
| `0002_create_chat_sessions.sql` | `chat_sessions` テーブル作成 |

### 適用状況の確認

drizzle-kit には適用状況を表示するコマンドがないため、`pnpm db:status` (`src/scripts/db-status.ts`) で確認します。

```
applied  0000_create_admin_users
applied  0001_create_users
pending  0002_create_chat_sessions
```

- drizzle-kit は適用済みのマイグレーションを `drizzle.__drizzle_migrations` に記録します。ファイル名は記録されず、`created_at` に `meta/_journal.json` の `when` が入ります。
- `db:status` はこの `created_at` と `when` を突き合わせて判定します。

### ロールバック

drizzle-kit には rollback がないため、`drizzle/down/<tag>.sql` に戻すための SQL を手書きし、`pnpm db:rollback` (`src/scripts/db-rollback.ts`) で実行します。

```sh
pnpm db:rollback   # rolled back  0002_create_chat_sessions
```

- 最後に適用したマイグレーションを 1 つ戻します。複数戻す場合は繰り返し実行します。
- down SQL の実行と `drizzle.__drizzle_migrations` の記録削除は 1 トランザクションで行います。途中で失敗した場合は何も変更されません。
- down ファイルがない場合は何もせずエラー終了します。
- 戻した後は `src/db/schema/` と DB が一致しない状態になります。`pnpm db:migrate` で再適用するか、マイグレーションを作り直します。

### マイグレーションの作り直し

マイグレーションのファイル (SQL / snapshot / journal / down) は git で戻します。
`drizzle-kit drop` は DB の適用状況を見ずに、順番も無視してファイルを削除できるため使いません。

1. DB に適用済みなら `pnpm db:rollback` で戻す (`pnpm db:status` で確認)
2. git でファイルを戻す
   - 未コミット: `git checkout -- drizzle/meta/_journal.json` し、追加された SQL / snapshot / down ファイルを削除する
   - コミット済み (マージ前の自分のブランチ): `git revert` または `git reset` で戻す
3. スキーマを修正し、`pnpm db:generate --name <name>` で生成し直す

マージ済みのマイグレーションは他の環境で適用済みの可能性があるため戻さず、修正用のマイグレーションを追加します。

### テーブル追加・変更の手順

1. `src/db/schema/` にテーブルを定義 / 変更する
2. 新規テーブルの場合は `src/db/schema/index.ts` から export する (リレーションが必要なら同じファイルに `relations()` で定義)
3. マイグレーションを生成する: `pnpm db:generate --name <name>`
4. 生成された SQL を確認し、`drizzle/down/<tag>.sql` に戻すための SQL を書く
5. 適用する: `pnpm db:migrate`。`pnpm db:rollback` → `pnpm db:migrate` で down が動くことも確認する
6. このドキュメントのスキーマ・マイグレーション一覧を更新する

その他のコマンドは [02_開発環境.md](./02_開発環境.md) を参照してください。
