# 構成

## 技術スタック

| 用途 | ライブラリ / ツール |
| --- | --- |
| ランタイム | Node.js (`containers/api/local/Dockerfile`) |
| Web フレームワーク | [Hono](https://hono.dev/) + `@hono/node-server` |
| ORM | [Drizzle ORM](https://orm.drizzle.team/) (`node-postgres` ドライバ) |
| マイグレーション | drizzle-kit |

| 管理画面 | `@sson0-er/drizzle-admin` (Django Admin 風のサーバーレンダリング CRUD) |
| LLM | LangChain (`@langchain/openai`) |
| WebSocket | `@hono/node-server` の `upgradeWebSocket` + `ws` |
| 言語 | TypeScript (ESM, `module: NodeNext`) |
| Lint / Format | Biome |
| パッケージマネージャ | pnpm (サプライチェーン攻撃対策の設定は [02_開発環境.md](./02_開発環境.md) を参照) |
| 開発時実行 | tsx (`tsx watch`) |

## ディレクトリ構成

```
api/
├── docs/          # このドキュメント
├── drizzle/       # drizzle-kit が生成するマイグレーション (Biome 対象外)
│   └── down/      # ロールバック用 SQL (手書き)
└── src/
    ├── index.ts       # エントリポイント。サーバー起動
    ├── env.ts         # 環境変数の読み込み
    ├── entrypoints/   # 外部からの入口 (HTTP / WebSocket)。業務ロジックは置かない
    │   ├── app.ts       # ルーティング (管理画面と routes/ を機能ごとの接頭辞にマウント)。RPC 用の AppType を export
    │   ├── middlewares/ # 一部のルートにだけかけるミドルウェア (認証など)
    │   └── routes/      # パスごとの処理。<機能>/index.ts が機能ごとにまとめる
    ├── apps/          # 業務ロジック。機能ごとにディレクトリを切る (normal_chat/ など)
    ├── admin/         # 管理画面 (開発者用のため entrypoints/ には含めない)
    ├── db/            # DB クライアントとスキーマ
    ├── libs/          # アプリケーションに属さない薄い共通部品
    │   ├── agents/    # LLM に投げるチェーンの組み立て (system メッセージ・履歴・入力のプロンプト + tools / 構造化出力)
    │   ├── external/  # 外部サービスのクライアント (llm/: LLM。モデルごとの実装は llm/models/)
    │   ├── prompts/   # prompt_templates.yaml の読み込み
    │   ├── queries/   # 名前を付けて切り出した Drizzle のクエリ
    │   ├── tasks/     # 接続やリクエストから切り離したバックグラウンド処理
    │   └── websocket/ # WebSocket で送るメッセージの形式
    └── scripts/       # CLI スクリプト。`pnpm <group>:<name>` → `scripts/<group>/<name>.ts` (`chat_session/` は入力を短くするため `session:`)
```

### 規約

- ESM のため、相対 import には `.js` 拡張子を付ける (例: `src/index.ts` の `./entrypoints/app.js`)。
- 親ディレクトリをたどる import (`../`) は書かず、`src/` からのパスに `#` を付けて書く (例: `#libs/queries/chat-sessions.js`)。どの層を参照しているかを import 文から読み取れるようにするため。同じディレクトリ以下は `./` のままにする。
- `#` は `package.json` の `imports` で、通常は `src/`、`production` 条件 (`pnpm start`) では `dist/` を指す。tsx は `src/` の `.ts` をそのまま読み、`tsc` は `dist/` を指すパスを `src/` のソースに読み替えて型を解決する。
- ファイル名は kebab-case にする (例: テーブル `chat_sessions` → `chat-sessions.ts`)。
- テーブルは `src/db/schema/` にテーブルごとに定義し、`src/db/schema/index.ts` から export する。
- 共通カラムは `src/db/schema/columns/` に置き、スプレッドで利用する (`...timestamps`)。
- 全体にかけるミドルウェアとエラーハンドリング (`app.onError`) は `src/entrypoints/app.ts` に置き、routes/ 側には書かない。
- ユーザー向けのエンドポイントは `src/entrypoints/routes/<機能>/` に、1 ファイル 1 パスの Hono アプリとして定義する。接頭辞より後ろのパス (`/db` など) は各ファイルで定義する。
- 機能内のファイルは `routes/<機能>/index.ts` で 1 つの Hono にまとめ、`src/entrypoints/app.ts` ではそれを機能の接頭辞 (`/health` など) にマウントする。`app.ts` には機能ごとに 1 行だけ並ぶようにするため。
- ファイル名は URL に合わせる必要はなく、分かりやすさを優先する。ファイル名は `<メソッド>-<リソース名>.ts` にし、export する Hono アプリの名前もこれに揃える (例: `GET /health` → `routes/health/get-health.ts` の `getHealth`、`GET /health/db` → `get-health-db.ts` の `getHealthDb`、`POST /chat_session` → `routes/chat_session/post-chat-session.ts` の `postChatSession`)。WebSocket はメソッドを意識しないため、メソッド名を付けない (例: `/ws/normal_chat/:sessionUid` → `routes/normal_chat/normal-chat.ts` の `normalChat`)。
- RPC クライアント (`hono/client` の `hc`) が型を拾えるよう、各ファイルのルートは `new Hono().get(...)` のようにチェーンで定義し、`index.ts` と `app.ts` でもマウントをチェーンでつないで `app.ts` から `AppType` として export する。`app.get(...)` のように文を分けて書くと型にルートが残らない。
- 認証など一部のルートにだけかけるミドルウェアは `src/entrypoints/middlewares/` に置き、各ルートのハンドラの前に指定する。ユーザー向け HTTP API は `Authorization: Bearer <users.uid>` で認証し (`require-user.ts`)、ハンドラでは `c.var.user` を使う。
- WebSocket エンドポイントも `routes/` に置き、`/ws/<name>` にマウントする。`@hono/node-server` は WebSocket の実装を持たないため、`src/index.ts` の `serve` の `websocket.server` に `ws` の `WebSocketServer({ noServer: true })` を渡している。
- チャットの WebSocket はパスの `chat_sessions.uid` で会話を判別する (例: `/ws/normal_chat/:sessionUid`)。該当するセッションがなければ upgrade せず 404 を返す。

### チャットの WebSocket 通信

- 1 接続で受け付ける質問は最初の 1 つだけ。2 つ目以降の受信は捨てる。
- サーバーは回答を `{"message": {...}}` で送る。1 つの回答はストリーミングで複数回に分けて送り、最後に `stop: true` を送る。1 つの質問に複数の回答 (エージェント) が返ることがあるため、`stop` は回答ごとの終わりにすぎない。
- すべての処理が終わったら `{"done": true}` を送る。接続を閉じるのはクライアントの責務で、`done` を受け取ったら閉じる (`src/scripts/chat_session/normal-chat.ts` が例)。
- 会話の保存は `done` より前に終えている。`done` を受けたクライアントがすぐ次の接続で質問しても、前の質問が履歴に入っているようにするため。
- `WS_TIMEOUT_SECONDS` を過ぎるとサーバーから閉じる (code 1000, reason `timeout`)。想定外のエラーは code 1011 で閉じる。
- 切断・タイムアウトでは `AbortSignal` で LLM の呼び出しを止め、そこまでに生成した回答を保存する。
- メッセージの形式は `src/libs/websocket/sender.ts` にまとめる。`libs/` と `apps/` が Hono に依存しないよう、送信先は `send` だけを持つ型 (`WsSender`) で受け取る。`null` を渡すと送らずに回答だけを返すので、テストや評価・バッチから同じ処理を呼べる。

### バックグラウンド処理と終了

- 回答後のログなど、クライアントを待たせる必要のない処理は `runInBackground` (`src/libs/tasks/background-task.ts`) で接続から切り離す。接続のタイムアウトや切断で止まらない。
- `src/index.ts` は SIGTERM / SIGINT を受けると新しい接続の受け付けをやめ、実行中のバックグラウンド処理を `BACKGROUND_TASK_SHUTDOWN_TIMEOUT_SECONDS` まで待ってから終了する。Promise は外から止められないため、待ちきれなかった処理はログに出してプロセスの終了とともに打ち切る。

## 今後の方針

### 業務ロジック (`src/apps/`)

- 業務ロジックは `src/apps/` に機能単位で置く。`apps/` は Django の app や `chat-on-fastapi/api/apps/` と同じ意味で、モノレポのデプロイ単位ではない。
- 依存の向きは `entrypoints/` → `apps/` → `db/` とし、`apps/` は Hono に依存させない。
- チャットの機能は次の 3 層で組む (例: `apps/normal_chat/`)。
  - `<機能>-controller.ts`: entrypoints/ から呼ばれる入口。flow を実行し、後処理の切り離しと `done` の送信を行う。
  - `flows/`: LangGraph のグラフでノードをつなぎ、最後に会話を保存する。途中で止まっても、そこまでの回答を `finally` で保存する。
  - `nodes/`: 1 つのエージェントで回答を生成して送る。回答は flow と共有する `FlowData` に書く。
- プロンプトは機能ごとの `prompt_templates.yaml` に `flow 名 > node 名 > agent 名` で書き、flow のモジュールで `setStore` して読み込む。flow 名は全機能で重複させない。

### 共通部品 (`src/libs/`)

- `libs/` には、アプリケーションに属さない薄い共通部品を置く。`apps/` と違い機能単位ではない。
- 依存の向きは `entrypoints/`・`scripts/`・`apps/` → `libs/` → `db/` とする。`libs/` から `apps/` と Hono は import しない。
- 特定の場所でしか使わないもの (例: `src/admin/password.ts`) は `libs/` に移さない。

#### クエリ (`src/libs/queries/`)

- Drizzle のクエリに名前を付けて切り出す場所。ファイルはスキーマに合わせてテーブルごとに作る (例: `libs/queries/chat-sessions.ts`)。
- すべての DB アクセスをここ経由にはしない。Drizzle は直接書いても読みやすいため、置くのは複数箇所で使うものや、条件・トランザクションが込み入っていて名前を付けたいものだけにする。
- アクセスを集約する層ではないため、`repositories/` ではなく `queries/` という名前にしている。
- `db` は直接 import して使う。呼び出し元から引き回さずに済むようにするため。トランザクションの中で呼べるよう、最後の引数に省略可能な `db` (型は `src/db/index.ts` の `Executor`、既定値は import した `db`) を受け取り、`tx` を渡せるようにする。
